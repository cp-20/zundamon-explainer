# シーンを並行で作らせる

見本のシーンが通ったら、残りのシーンをシーン担当のエージェントに並行で作らせる。

## 分け方

- 1 担当あたり 1〜2 シーン。隣り合うシーンでつなぎ目が複雑なものは同じ担当にする。
- 計画の時点で「シーンのつなぎ目の表」 (各シーンの最初と最後の画面) を `AGENT_BRIEF.md` に書いておく。
- 担当は `PLAN.md`、`AGENT_BRIEF.md`、見本のシーンのコードを読んでから書き始める。

## 担当への指示 (`AGENT_BRIEF.md`)

[templates/AGENT_BRIEF.md](templates/AGENT_BRIEF.md) を写して、動画ごとの部分 (データの関数、色の約束、つなぎ目の表、見本で決まった基準) を書く。
共通の内容は docs を読ませる。依頼文に入れること：

- 担当のシーンとファイル名、PLAN.md の節。
- そのシーンで使う実データと、`assert` で確かめる数字。
- 画面の大きさの目安 (本文 34〜48px、中央の領域も使う)。担当は小さく作りがち。
- 「指示を過剰に読み取らない。計画どおり最小限に作り、図を見れば分かることを文字にしない」。
- 共通部品 (`zunda/`、`config/`、`tools/`、`bin/`) と他のシーンは変更しない。不具合は報告に書く。
- 1080p では描かない。`bin/pipeline.sh <name> SNN` (540p) で検査 0 件まで直し、シートとフレームを目で見る。
- 報告に書くこと：作ったものの流れ、尺、台詞を変えた所と理由、検査の結果と目で見て直した所、確かめていない所。

## 届いたものの見方

- 報告を信じすぎない。必ず自分でシートを見て、必要ならフレームを切り出す。
- よくある直し：
  - 文字・図が小さく、上の帯だけに詰まっていて、中央の領域が空いている。
  - いちばん見せたい現象が見えない (データの選び方が悪い、比べる尺度が悪い)。
  - 重要な場面が 1 歩ずつになっていない (手順が一気に進む)。
- 直しは、具体的な大きさ・位置・見せ方を書いて同じ担当に頼む。直ったら、もう一度シートを見る。

## 気をつけること

- 担当は 540p の試写を何度も回す。同時に動かす数は 6 程度まで。
- 担当が「自分の起動した処理を待つ」ときに `pgrep -f pipeline.sh` のような待ち方をすると、待っているコマンド自身に一致して終わらない。
  担当が長く報告してこないときは、出力ファイルの更新時刻を見て、止まっていないか確かめに行く。
- 何人かが同時に共通の出力 (`build/sheet` など) を書くと、まれに壊れたファイルを読む。単独で回し直せば直る。
- 担当がつなぎ目の画面を守っているかは、通しのあとでつなぎ目の差を測って確かめる。
